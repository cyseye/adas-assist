# Postmortem 协议

> 任务/项目级复盘协议：OODA 前端决策环 + Postmortem 五要素 + 根因分析法。对象是项目任务，非 skill 资产。

## 核心原则

- **对事不对人**：根因分技术根因 + 流程根因，不追责个人。
- **事实先于归因**：Observe 步只记事实，Orient/根因步才归因。
- **闭环驱动**：每条根因必对应 CAPA action，每 action 必有 owner+due+验证标准。
- **可复用**：教训（Lesson）是可复用认知，非具体 action。

## OODA 四阶段

| 阶段 | 动作 | 产出 |
|------|------|------|
| Observe（观察） | 收集时间线/症状/影响/客观数据，只记事实不归因 | 事实清单 |
| Orient（判断） | 严重度分级；查历史 postmortem 判复发；选根因法 | 严重度+根因法+是否全量复盘 |
| Decide（决策） | 是否全量 postmortem；根因分歧大→转 consensus | 决策（复盘/转交/退出） |
| Act（行动） | 根因分析→五要素→CAPA→沉淀 | postmortem.md + capa.md |

## Postmortem 五要素

| 要素 | 作用 | 必填 |
|------|------|------|
| 症状(Symptom) | 可观测的异常表现 | 是 |
| 根因(Root Cause) | 技术根因 + 流程根因（附 5Why/鱼骨链） | 是 |
| 影响(Impact) | 范围/时长/波及面 | 是 |
| 行动(Action) | 指向 capa.md 的 action_id 列表 | 是 |
| 教训(Lesson) | 可复用认知（非具体 action） | 是 |

## 根因分析法

### 5Why（简单/单链路问题）

逐层追问"为什么"，**每层必有依据**（数据/日志/代码/事实），缺依据则标 `[假设]` 并降级为待验证。

```
症状 → 为什么1（依据）→ 为什么2（依据）→ ... → 根因
```

规则：
- 每层"为什么"的答案必须有证据支撑，禁止凭空推断
- 连续问至根因（非个人失误，而是系统/流程/技术缺陷）
- 若某层缺依据，标 `[假设]`，后续需验证后回填

### 鱼骨图（复杂/多因素问题）

六分支：人(Man)/机(Machine)/料(Material)/法(Method)/环(Environment)/测(Measurement)。

每个分支列可能因素，逐因素验证是否真实贡献，排除无关项，保留贡献项入根因。

规则：一因素需有证据才入根因，否则标 `[待验证]`。

## 严重度分级（1-4）

| 级别 | 标准 | 是否复盘 |
|------|------|---------|
| 1-致命 | 服务中断/数据丢失/安全泄露 | 必复盘 |
| 2-严重 | 核心功能受损/延期里程碑 | 必复盘 |
| 3-一般 | 非核心功能受损/可绕过 | 选复盘（复发则必复盘） |
| 4-轻微 | 局部/可轻松回退 | 不复盘（`[INFO]` 退出） |

## 值得复盘的判定

满足任一即复盘：
- 严重度 ≥ 3
- 同类别问题历史已记录后再发（复发）
- 造成 Knowledge/Memory 可沉淀的认知
- 团队需对齐口径避免重复踩坑

不复盘：严重度 4 且无复发性、纯偶发、无可复用认知。
