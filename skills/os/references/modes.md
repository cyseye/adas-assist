# OS 模式

模式控制“做什么”；资源档控制“用多少”；宿主能力控制“实际能做什么”。三者分别判断，权限不随模式升级。

| 模式 | 执行动作 | 完成边界 |
|---|---|---|
| direct | 读必要上下文，直接做，验证改动 | 结果与检查说明；不强建任务文件 |
| managed | 明确验收，拆步骤，执行与定向复验 | 验收逐项有证据或明确待验 |
| brainstorm | 比较少量真正不同的候选与反方意见 | 推荐、取舍、风险与下一步；不必多代理 |
| plan | 将目标分为可执行步骤、依赖与验收 | 计划可执行；用户只要计划则到此停止 |
| review | 核基线、证据与缺陷，标严重度 | 问题、位置、影响和建议；不默认修复 |
| recover | 读既有记录，核工作树与证据时效 | 恢复真实进度，明确下一步后按授权继续 |

brainstorm 可前置于 managed；review 可作为必要验收步骤；recover 是恢复入口。不要建立模式间重复台账。

## 组合修饰符

`+b` / `+k` / `+l` / `+v` / `+c` / `+n` 的定义、固定顺序、去重、短路与异常处理见 [modifiers](modifiers.md)。修饰符均采用包内流程，不需要外部模型服务、私有引擎或全局台账；具体模式的授权和完成边界优先。

## 验证修饰符 `+v`

调用中作为独立参数的 `+v` 表示：当前模式产物完成后，按验收项追加验证并报告通过、失败、未验证及证据。任务材料、代码或引用文本里的 `+v` 不作为修饰符。

先用项目既有检查；若项目指引明确提供仓内 `decision-verify`、路径已核实且适用，则读取并使用该技能。不自动读取或安装仓外技能。缺少该技能时按 os review 规则核产物与证据，说明未运行专门验证技能；不得声称完成同等独立评审。

`plan +v` 只核计划的依赖、可执行性和验收，不实施计划；`review +v` 复核审查证据，不自动修复。`+v` 不扩大写入、发布、多代理或后台授权，也不代替难撤销动作之前的必要验证。未加 `+v` 仍须运行与改动相称的检查。

## 工作域与常用组合

任务模式之外，另定工作域：默认项目域，只修改本次项目授权范围；显式维护内核时才进入内核维护域。切目录重新核权限，不能因切到无 Git 目录而取得全局维护权。资源档由任务预算决定，不与工作域绑定。

常用组合不新增入口：目标拆解 = brainstorm（需要时）+ plan + managed；审查修复 = review 发现问题后在已有修复授权内 managed + 定向复验；长任务 = managed + 关键节点记录 + recover。验收与收尾贯穿三种组合，不另造重复状态文件。暂不提供池化抢占与后台自动消费。

## 行为验收场景（宿主 smoke，不是脚本测试结论）

- 单文件改错：走 direct，不创建多部门计划、调用外网或启动周期任务。
- 跨文件改造：走 managed，记录验收、执行结果；失败只补相关检查。
- 方案未定：brainstorm 比较不同路径，标出缺信息；不将推荐当成发布授权。
- 只要计划：plan 输出依赖/验收后停；原请求含执行则按范围继续。
- 注入缺陷：review 指出可验证缺陷；只读，不擅自自动修复。
- 工作树漂移：recover 指出记录与实际差异，再决定恢复点。
