# ADR 写作指引

> 五要素的写法约束与常见反模式。目标：让 ADR 简短、可追溯、能被后人快速读懂决策理由。

## Context（背景）怎么写

写「当时的处境」，不写「解决方案」。回答：
- 要解决什么问题？（一句话问题陈述）
- 有哪些约束？（技术 / 时间 / 团队 / 兼容性 / 合规）
- 驱动因素是什么？（性能？成本？可维护性？上线压力？）
- 当时已知的事实 / 假设

> 长度参考：1-3 段。背景是 ADR 价值最高的部分——决策会被推翻，但「当时的约束」是历史真相。

## Decision（决策）怎么写

用肯定句陈述「我们决定 X」，再写「为什么是 X 不是其他」：
- 明确 chosen（采纳项）
- 关键理由（与 Context 的驱动因素对应，2-4 条）
- 避免含糊（「考虑各方面后决定」不算决策）

## Consequences（后果）怎么写

诚实写三类影响：
- **正向**：决策带来的好处
- **负向**：付出的代价 / 引入的风险 / 技术债
- **中性**：随之而来的约束 / 需跟进的事项

> 只写正面的后果是最大反模式——失去「可追溯」价值。

## Alternatives（备选）怎么写

列 2-3 个认真考虑过的备选，每个写：
- 方案一句话
- 拒绝理由（与 Context 约束挂钩）

> 没有备选的决策显得随意；记录备选让后人不必重新论证已排除的路。

## 反模式

| 反模式 | 正确做法 |
|--------|---------|
| Context 写成方案描述 | Context 只写背景与约束，方案放 Decision |
| Decision 无理由 | 必附 2-4 条与驱动因素对应的理由 |
| Consequences 只写正面 | 正向 / 负向 / 中性三类都要 |
| 无 Alternatives | 至少列 1-2 个备选 + 拒绝理由（重大决策必填） |
| 改已 Accepted 的正文 | 新认知另起 ADR 并 Supersede，不动旧正文 |
| 一份 ADR 多决策 | 一决策一文档 |
| 决策无结论就沉淀 | 先有结论（consensus/PCF/用户）再 record |
| 写成 PRD / 设计文档 | ADR 只记「决策 + 理由」，不展开实现细节 |

## 经验汇总文档（decisions/experience/，本地特例）

session-review 的 `experience-summary-due` 信号触发（距上次「经验汇总」文档 >90 天 且 meta 域新增 ≥3 份）时，产出汇总型**文档**落 `decisions/experience/`（仅本地，非 ADR、无 frontmatter 状态机、不入 KNOWLEDGE 索引），文件名固定含 `experience-summary` + 年月（供扫描器定位），title 含「经验汇总」：

- **来源**：本期来源清单——参与汇总的 EVOLUTION.md 文件 / 信号处理记录 / 新 ADR 编号
- **正文**：提取的稳定经验，每条格式「结论一句话 + 落点」（落点枚举：CLAUDE.md 纪律 / standards 某文件 / 某 skill 条款 / 已建 ADR 编号 / 维持现状的理由）；尾部附未消化项清单，留待下期
- **汇总后动作**：各 skill EVOLUTION.md 按惯例滚动（摘要表保留、细节清）；新汇总取代旧汇总时物理删除旧文件

## 长度与粒度

- 单份 ADR 控制在 1-2 屏（约 30-80 行正文）
- 超长说明混入了实现细节 → 移入 references 等附属文件，ADR 只留决策
- 太短（<10 行）说明 Context / Consequences 没写透

## 文风

- 简洁陈述句，避免主观情绪词
- 用「我们决定 / 代价是 / 风险为」，不用「希望 / 也许 / 尽量」
- 事实与观点分开：Context 重事实，Consequences 可含预判
