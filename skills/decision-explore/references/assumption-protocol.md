# 假设陈述协议

> 未澄清的需求点不能「默认」处理，必须显式记录为假设。假设错误是返工的主因，写下来才能被复核和证伪。

## 核心原则

**禁止隐式假设**：任何「我猜应该是…」「通常是这样」的判断，都必须写入 clarified-requirements.md 的假设节，不能只留在脑子里。隐式假设一旦错误，往往到交付才暴露，代价最高。

## 假设六要素

每条假设必须包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| 陈述 | 假设是什么（一句肯定句） | 「资源数据量级在万条以内」 |
| 依据 | 为什么这么假设 | 「参照现有同类看板的数据规模」 |
| 影响 | 假设错误会影响什么 | 「若超十万条，分页方案需改为游标」 |
| 可证伪性 | 如何能证明它错 | 「查询生产表 count」 |
| 验证方式 | 何时 / 如何验证 | 「上线前查一次生产数据」 |
| 风险 | 假设错误的严重度（高 / 中 / 低） | 高（影响核心交互） |

## 风险分级

- **高**：假设错误会推翻方案核心或导致大面积返工 → 必须在实现前验证
- **中**：影响部分设计，但有 workaround → 标注，实现时复核
- **低**：影响小，易调整 → 记录备查即可

## 何时把不确定项转假设

- 用户无法回答或表示不确定
- 答案依赖外部信息（生产数据、第三方行为）暂不可得
- 多种解读都合理，用户未明确选择 → 选默认解读 + 标假设

## 反模式

| 禁止 | 正确做法 |
|------|---------|
| 「这个不用写，大家都知道」 | 写下来，常识也可能错 |
| 假设无依据、无验证方式 | 六要素缺一不可 |
| 高风险假设不标记 | 高风险必须标「实现前验证」 |
| 把假设混进确认的需求里 | 假设节与需求节分开 |
